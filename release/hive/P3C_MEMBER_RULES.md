# P3c: member restrictions on an owned mind

An enabled, currently signed-in member can add an `ask` or `deny` rule only at `agent:<mind id>` while they own that live mind. The server resolves the persisted person for every `user:<suffix>`; spelling does not confer membership. A synchronous trusted host callback re-reads the session before target lookup and again inside the existing per-mind lock and control database transaction. The same person must still be signed in, still be an enabled member, and still own the nondeleted mind when the write occurs. Client input supplies only scope, skill, mode and an optional text note; it supplies neither identity nor provenance.

The host writes `origin: member` and `granted_by: <current person>`. Restricted deletion reads the stored row, locks its recorded mind, rechecks current authentication and ownership, and rejects a concurrently changed row. It deletes only an `ask`/`deny` with that host origin and the same creator. A new owner cannot delete the previous member's row through this path; losing ownership also removes the original creator's restricted deletion authority. An expired own member rule remains removable by id. Admin, role, template, answer, legacy and another person's rules remain outside this path.

Member writes do not supersede or expire other rules. The evaluator remains unchanged: nearer scope, then exact skill before a glob, then the more restrictive mode. An exact member `ask` therefore beats an ordinary same-scope glob `deny`; a competing exact `deny` still wins a same-specificity tie. P2's template ceiling remains a separate first gate, including refusal when current template authority cannot be read. Existing discovery, explicit-only and human-only behavior is retained.

Generic trusted `add_rule`/`delete_rule`, global `role_of`/`policy_writer` authority and evaluator functions are retained unchanged. The app integration must require current existing host admission as well as the enabled matching person row before ordinary-member dispatch, positively validate the session, and preserve identity across the body await and transaction callback. A still-stored person/session does not restore a revoked family-SSO allowlist admission. Valid local-password, family/admin and hive-owner powers retain their existing privileged route; a matching member row does not rewrite global family-admin semantics. Policy list/audit behavior is unchanged. New member writes refuse the leading `role:` note namespace because existing role reapplication deletes rows in that namespace; ordinary notes remain data. Notices use `after_commit`, so rollback exposes neither a committed row nor a policy-update event.

Only the new member POST path uses the existing streamed JSON reader with a 64 KiB cap; the existing privileged policy body path is unchanged. The member body is closed to scope, skill, mode and note. Session kind/expiry/identity and current host role are checked before dispatch and after body/at the member write transaction. Nonhuman or malformed authority does not inherit a fallback operator identity.

Program actions have a separate rule resolver. It applies the existing `restrictiveness` ordering after program scope and exactness, keeping its existing timestamp tie for equal modes, so an older exact same-scope allow no longer beats a newer member ask or deny. Program-only filtering, HUMAN_ONLY, no-rule default denial and the P2 before/after ceiling wrappers are unchanged. The general Policy functions are unchanged.

## Tests

`hive/tests/test_member_rules_p3c.py` uses real HTTP with the existing fake process driver. It covers client provenance rejection, no allow or foreign scope, current ownership, creator/origin deletion, stale body and lock authentication through the streaming-body seam, rule replacement, rollback and post-commit events, role reapplication, precedence, the real template-rule store, and `ProgramActions.decide` with a stored older allow against a new member ask or deny. An arbitrary-suffix case exercises the trusted central helper directly; the other HTTP cases use real member identities. All data is synthetic.
