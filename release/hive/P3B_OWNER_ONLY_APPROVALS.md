# P3b: opt-in owner-only approval answers

Set a mind's `options.approvals` to `owner_only` to make its actual owner the sole person allowed to approve, deny or give any five-way answer. Omit that option for existing behavior. An owner clears it by an explicit full options replacement without the field; malformed values are refused. Existing key-lock confirmation still applies. Only the current owner may change this flag, including when a full replacement would drop it; admin and hive-owner privileges do not bypass that rule. Trusted host creation paths must supply the owner's `by` identity when creating an opted-in mind.

The flag is part of existing options storage; no database column or migration is added. The canonical Hive create/update paths check transitions under the mind lock and repeat current host authentication at the exact guarded database write. HTTP checks after the request body refuse an unauthorized setting transition before unrelated request effects. Existing arbitrary trusted direct database writes are not a new public interface.

All three approval answer routes use current session/visibility checks after body parsing and again at the synchronous write boundary. The central Policy guard independently reads the current mind owner and flag. Once, For, Always, No and Never, `/approve` with or without remember, `/deny`, and program-action approval rows pass the same guard. Status and any durable answer rule commit in one short transaction under the mind lock, before notification awaits; a failed durable rule write rolls back status. Notifications and the existing governance/MeTTa audit remain outside that database transaction. No lock spans an await.

Admin audit/list/track-record visibility stays available. It does not confer answer authority on an opted-in mind. The person decisions read projection omits approvals this person cannot answer; ordinary audit endpoints still show them within existing visibility. Defaults retain current visible once-only answers and existing durable owner/admin/hive-owner rules. Program exact-only and high-risk restrictions and the P2 ceiling remain in force; an owner-only setting is no permission grant. The ordinary rule evaluator is unchanged.

Session hardening here is scoped to the new owner-only/setting write path, using the existing human-session contract plus current matching people rows across all principal suffixes. It does not rewrite global family SSO roles or downstream execution/redeem semantics. Existing approval delivery and program callbacks remain informational after an authorized committed answer.

Key deletion does not overwrite a newer protection. Its worker re-reads the options under the existing tools-choice and mind fences and removes only a still-matching unlocked key through the existing locked writer. A new approval flag, a different assigned key or a fresh key lock survives an older removal request; no stale full-options replacement clears a newly protected flag. This is a field merge, not a new credential or key-route authorization protocol.

## Tests

`hive/tests/test_owner_only_approvals_p3b.py` covers every answer route across owner, member, admin and hive-owner callers and ordinary and program rows; genuine stored hive-owner authority; setting transitions and malformed values; defaults, audit and actionability; body and handoff invalidation; durable-write rollback and pre-notification ordering; the ceiling and high-risk constraints; and queued key-removal cases that change the flag, the key or the lock, or revoke the owner's session, before the worker begins. All data is synthetic.
