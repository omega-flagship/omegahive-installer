# OmegaHive installer on a real Ubuntu machine: hive-1 trial, 2026-10-28

*Written by the team lead's agent on Kabir Veitas' instruction (AI-assisted). Linked issue: omega-flagship/omegahive-installer#2.*

## What was run, where

- **Machine:** omega-hive-1, a plain cloud VM, not a GitHub runner: Ubuntu 22.04.5 LTS, kernel 5.15.0-198, x86_64, 4 vCPU, 16 GB RAM, 96 GB QEMU virtual disk (rotational, writes measured under 1 MB/s during the install), fresh `apt upgrade` and reboot before the trial, ufw active with only 22/tcp open.
- **Installer:** `omegahive-linux.sh` as served by release `linux-test-20261028-r12` at 22:08Z, sha256 `191344a8d22272e180b71c1040113d1e4a8877654b74b6a3f09ef70e35ff1ead` (90,803,922 B; byte-identical to `ci/kit/omegahive-linux-r13.sh` at `c7e98f4`). Checked against the release's `.sha256` and the pinned hash on the VM before the run.
- **User:** a fresh account `hive-test-1` with a sudoers drop-in allowing only `/usr/bin/apt-get` and `loginctl enable-linger hive-test-1` without a password, exactly as the repo's `kit-r13` CI job gives its runner user. No seeding of SWI-Prolog (r13 bundles it).
- **Command:** the guide's one line, `sh ~/omegahive-linux.sh`, run as that user under `script` so the installer sees a terminal. Every step was approved by Kabir and run by hand over SSH; the runbook was reviewed by the QA agent before anything ran.

## Run 1 (22:12Z): exit 64 after 18 min 7 s

What worked, with no password prompt: apt packages (build-essential, cmake, ninja, libedit-dev, libyaml-dev, zlib1g-dev and the rest), SWI-Prolog built from the bundled source, the bundled CPython 3.12.16 runtime, the venv with the hive's packages, the user unit installed and enabled, linger on.

What failed: the last step, which starts `omegahive.service` and waits for its first control reply. `deploy/linux/control.py` bounds that wait at 15 s (`HELLO_READY_SECONDS = 15`). The hive needed 42 s from `Started OmegaHive private local-owner hive` to `Uvicorn running on http://127.0.0.1:8700`, creating `hive.db` and the rest of its data directory on this disk. The installer wrote `bootstrap-failure-…json` (`reason: control_reply_timeout`), printed "OmegaHive couldn't finish setting up … A setup step could not finish or was cancelled" and exited 64, while the hive came up 27 s later and kept running (enabled, listening on 8700, `/api/health` 401). `omegahive status` then said "Setup is incomplete. Run the installer again, or … uninstall". Issue #2 has the detail and a suggested fix.

Also in the log, not blocking: `Could not find platform dependent libraries <exec_prefix>` from the bundled Python during the venv step.

## Run 2 (22:34Z, "run the installer again"): exit 0 after 15 min 44 s

The re-run does not resume: it stopped and disabled the hive, kept the apt packages, rebuilt SWI-Prolog and the venv, reinstalled the unit and bootstrapped again. This time the hive answered 2.3 s after the service start, because its data directory already existed, so the 15 s bound held. The installer printed the tunnel instruction and the one-minute sign-in link and exited 0.

## The host afterwards

- `omegahive status --json`: running, local owner, port 8700, source revision `15f3f9a1`.
- Listening: `127.0.0.1:8700` only. The hive refuses any other Host (HTTP 421 `wrong_host`), which is as designed.
- `loginctl`: Linger=yes; `systemctl --user`: `omegahive.service` enabled and active.
- Disk: 639 MB under `~/.local/share/omegahive` (runtime, venv, release, data); apt packages on top; plus two unpack directories the wrapper leaves in `/tmp/omegahive-installer-*` (about 68 MB each, one per run), which nothing removes.
- Sign-in: the exchange the CI job performs (`POST /api/auth/local/exchange` with the link's code and the link's port as Host and Origin) answered HTTP 200.

## In the browser

Kabir Veitas signed in from his own laptop the way the guide says: the SSH tunnel to the VM, `omegahive open` on the VM as the test user, the one-minute link pasted into the browser, then the UI at the tunnel's local address. ## Peculiarities of running on a VM, as found tonight

1. **The disk sets the pace.** On this VM (virtual disk, under 1 MB/s during the install) the first install took 18 minutes and the second 16, most of it building SWI-Prolog and the venv while one core sat in I/O wait. The installer's "about 15 minutes" is honest for fast disks and short for slow ones.
2. **The first start of the hive can exceed the installer's patience.** The 15 s hello bound (issue #2) is the only step that failed. A second run of the installer succeeds because the data directory then exists, at the price of a full rebuild (the re-run keeps apt packages only).
3. **Nothing is reachable from outside, by design.** The hive listens on `127.0.0.1:8700` and refuses any other Host with HTTP 421. The VM had ufw active with only 22/tcp open, and nothing had to be opened: the SSH tunnel in the guide is the whole access path. This also means headless testing from another machine or container has to go through SSH, not the network.
4. **Sudo is needed for exactly two things**, both done through the sudoers rule above without a password prompt: `apt-get` (update and install of the build packages) and `loginctl enable-linger <user>` so the hive survives logout. A user with no sudo at all would stop at the first.
5. **Preparation of the VM was manual:** `apt upgrade` plus a reboot for a pending kernel update, and ufw. Neither is the installer's business, but a newcomer on a fresh VPS image meets both.
6. **Leftovers:** two `/tmp/omegahive-installer-*` directories (about 68 MB each) from the two runs, not removed by the installer; the apt packages; 639 MB under the user's home. `omegahive uninstall` asks for `DELETE` on a terminal, so an automated teardown has to feed it.
7. **Ubuntu version:** 22.04.5 passed the installer's 22.04 gate; nothing newer was tried on real hardware.

A thought from Kabir for later, not for this release: a containerised form of the hive would make the VM path more straightforward, since the build, the user unit and the loopback rule would come packaged. Not the issue tonight.
